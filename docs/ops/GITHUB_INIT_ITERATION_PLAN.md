# github-init 分步迭代执行计划（门禁版）

> 目标：围绕 AI 托管全流程、终端/日志可观测性与堡垒机场景交互，按“单步闭环”迭代。  
> 原则：每一步都部署到 `34007`，由你验证通过后再进入下一步。

## 1. 执行规则（固定）

1. 单步范围：同一时间只做 1 个 Step，不跨步混改。
2. 门禁推进：`开发 -> 本地验证 -> 部署34007 -> 你验收 -> 下一步`。
3. 可追溯：每步记录分支、提交号、构建资源 hash、进程 PID、测试结论。
4. 风险前置：每步开始前先核对风险台账，确认本步风险控制项。
5. 回滚可用：每步必须保留可回滚点（提交号/构建时间/部署记录）。

## 2. 每步固定产物（固定模板）

1. 目标与不做项（本步边界）。
2. 变更文件清单（仅本步相关）。
3. 接口/行为变更清单。
4. 部署记录（34007）。
5. 验证清单（我测 + 你测）。
6. 风险更新（新增/关闭/遗留）。
7. 承上启下（下一步输入条件）。

## 3. 步骤总览

## S0 基线固化与记录体系（当前步骤）
- 目标：建立统一记录机制，锁定当前运行基线，避免“版本不清/结果不可复现”。
- 输入：当前 `github-init` 工作区。
- 输出：执行计划、风险台账、迭代日志（含 S0 基线）。
- 验收：后续每步都可按同一模板追踪。

## S1 部署可追溯
- 目标：解决“34007 当前到底是哪版”的确认问题。
- 输入：S0 基线记录。
- 输出：运行版本可视化（分支/commit/build_time），部署脚本化流程。
- 验收：
1. 页面或接口可直接看到运行版本。
2. 每次部署后可快速核对版本一致性。

## S2 交互骨架稳定（滚动/布局）
- 目标：修复 AI 托管会话面板滚动与布局稳定性。
- 输入：S1 可追溯能力。
- 输出：整面板与 tab 内容稳定下拉，避免首屏锁死/只显示一条。
- 验收：
1. 流程事件/CLI日志/步骤均可稳定滚动。
2. 工具栏可见性和内容区显示稳定。

## S3 流程事件与日志完整性
- 目标：事件/日志连续加载、顺序稳定、去重稳定。
- 输入：S2 稳定布局。
- 输出：持续下拉追加历史，不因轮询/切换丢内容。
- 验收：
1. 长会话可持续下拉查看历史。
2. 总条数与列表可见内容一致可解释。

## S4 托管控制闭环
- 目标：开始/暂停/恢复/CLI 恢复操作一致化。
- 输入：S3 完整事件流。
- 输出：控制动作、状态变化、流程事件三者一致。
- 验收：
1. 暂停/继续/恢复行为可复测通过。
2. 状态与事件轨迹可对齐。

## S5 项目集/项目/任务/会话联动
- 目标：管理视图与执行视图打通。
- 输入：S4 稳定状态与日志能力。
- 输出：从项目集到会话日志的一跳式追踪能力。
- 验收：
1. 统计面板可筛选和跳转。
2. 历史清单可定位至具体会话。

## S6 堡垒机参考交互优化
- 目标：结合 JumpServer/Teleport/Guacamole 交互模式提升效率。
- 输入：S5 功能闭环。
- 输出：关键事件锚点、快捷筛选、恢复入口统一、操作路径缩短。
- 验收：
1. 高频路径点击数下降。
2. 日志定位与恢复操作效率提升。

## S7 收敛与发布
- 目标：拆分提交、补关键测试、按验收结果 push。
- 输入：S0-S6 全部通过。
- 输出：清晰提交历史与可回滚版本。
- 验收：
1. 关键场景回归通过。
2. 按步骤提交并推送远端。

## 4. 效率控制（避免反复）

1. WIP=1：未完成当前 Step 不开启下一 Step。
2. 每步先出“最小可测版本”，先让你验证核心问题。
3. 不做“顺手优化”，所有新需求进入下一步计划。
4. 每步结束必须更新 `ITERATION_LOG` 与 `RISK_REGISTER`。
