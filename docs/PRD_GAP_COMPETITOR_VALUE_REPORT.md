# AI Coding Assistant：功能全貌 / PRD 对照 / 竞品与商业价值分析报告

> 版本：基于当前仓库代码（`backend/main.go` 注册的功能集合）与 `docs/PRD.md` 对照整理。  
> 说明：由于运行环境 `network_access=restricted`，本报告的“竞品搜索”以本地已存在的开源参考项目为主要证据来源，并结合产品常识推导；如需更完整市场信息建议补充在线调研。

## 1. 摘要（Executive Summary）

AI Coding Assistant（ACA）已经从 PRD 所定义的 “单用户 + 终端托管 + Kanban + 审批” MVP，扩展为更完整的 **AI Coding Agent Ops 平台**：

- **核心闭环**：任务 → 启动/关联终端 → 运行 AI CLI（Claude/Codex/Gemini）→ 自动检测状态 → 触发审批 → 规则/AI 决策 → 记录日志与审批审计 → 任务完成/异常 → 通知与复盘。
- **明显超越 PRD 的能力**：多用户与 RBAC、SSH 服务器与分组、规则集体系（system/task/terminal）、AI Provider 管理、日志导出、工作流/模板/AI workflow session。
- **当前最大商业风险**：基础可靠性与边界认知仍需进一步“产品化”收敛（例如 tmux 依赖的会话恢复、SSH 会话重启恢复缺失、多代理完整集成测试/验证不足）。

建议短期优先把产品定位收敛到：**并行终端 + 可控审批治理 + 可审计回放**，用明确指标完成商业验证，再决定是否加码“工作流编排层”。

## 3. 当前程序功能全貌（模块化梳理）

以下按“用户可感知能力 + 运营可控性”划分：

### 3.1 账号与权限（Auth / RBAC）
- 登录 / JWT / 鉴权中间件。
- 用户管理（管理员专属）：创建用户、角色（admin/user/viewer）、禁用/启用、查看最近登录等。
- 管理员专属高危能力：重置数据、SSH/Secrets 管理等（详见 `backend/main.go` 的路由组划分）。

价值：从“个人工具”升级为“团队可治理系统”的基础设施；也是企业付费最直接的门槛（权限/审计/隔离）。

### 3.2 任务与看板（Task / Kanban）
- 任务 CRUD、排序与展示。
- 状态不仅有 PRD 的 todo/in_progress/done，还扩展到 paused/failed/timeout/archived（更符合现实 agent 执行状态）。
- 任务详情聚合：终端、日志、审批记录、评论等。
- 任务自动化配置：工作目录、CLI 类型、初始提示、是否自动启动、是否自动创建目录（本地/远程）。
- AI 托管模式配置：托管提示词、结束条件、错误处理策略（见 `backend/model/db.go` 的 Task 字段）。

价值：把“agent 的一次性运行”变成可追踪的生产对象（任务），能量化吞吐、失败原因、复盘与协作。

### 3.3 终端托管（PTY / WebSocket / Scrollback / 日志）
- 本地 PTY 多会话、WebSocket 连接、输入/输出流式传输。
- 会话元数据（进程状态、AI 检测状态等）实时更新。
- 终端输出写库、终端日志面板与加载更早记录。
- tmux 恢复：重启后尝试恢复数据库中仍标记 running 的会话（但对运行环境 tmux 强依赖）。

价值：这是产品“可信执行面”的根基；终端交互可靠性直接决定用户是否愿意把 agent 工作流迁移进来。

### 3.4 AI 审核（审批治理）
核心能力：
- 终端输出检测到 “等待确认/权限提示” 等模式。
- 按规则集（system/task/terminal）执行 manual/auto_yes/smart 决策。
- 记录审批内容、响应、命中规则、AI 决策说明；并通过消息中心/审批中心暴露给用户复核。

价值：减少碎片化“yes/no”打断，且对团队场景提供安全治理（可审计、可追责、可回滚策略）。

### 3.5 AI 托管（任务自动启动 + 执行监控）
关键链路：
- 自动创建/进入工作目录；启动 CLI；必要时发送初始 prompt 或托管 prompt（包含完成条件标记等）。
- 后台监控任务完成/异常；遇到需要干预时可转为 paused 并通知。

价值：把“人的操作”降到最低，让 agent 从“辅助工具”变为“可运营产能”。

### 3.6 SSH / 远程执行面
能力：
- SSH Server 管理与分组、创建 SSH 终端会话。
边界：
- SSH 会话目前不支持重启后恢复（属于预期内限制，但需要在产品层显式告知）。

价值：适配真实生产环境（远程服务器、容器、CI 主机），是商业化的重要拓展点。

### 3.7 日志与审计（Logs / Export）
- 日志管理（会话列表、过滤/搜索）。
- 日志导出 API。
- 审批记录、AI 决策日志与统计面板。

价值：面向团队/企业的“合规与复盘资产”；也是“能证明价值”的数据基础（节省时间、降低风险）。

### 3.8 工作流与模板（Workflow / Template / AI Workflow Session）
能力：
- 工作流实体、模板、节点/运行记录、AI workflow session。
风险：
- 与“任务/终端”体系存在潜在产品认知割裂：用户应该用任务还是工作流？需要清晰定位与收敛，否则稀释核心价值。

价值：如果定位为“编排层/AgentOps OS”，这是可扩展空间；但短期可能拖累主线闭环。

### 4.2 PRD “版本规划”与现实落差
PRD 把 v1.0~v1.3 标为“已完成”，并把 v2.0 标为“多代理支持进行中”。从实现视角，v1.x 体系已基本齐全；但 v2.0 的“完整集成测试”仍是可靠性风险点（尤其当要商业化时）。

## 5. 商业验证：价值主张、付费点与指标

### 5.1 目标用户与典型场景
- 独立开发者：并行跑多个 agent 任务，减少切窗口和审批打断，快速复盘历史。
- 小团队：多用户权限、统一策略（审批/规则）、远程服务器执行、可审计与可追溯。
- 更长线（企业）：合规审计、策略治理、数据留存、权限隔离与成本控制。

### 5.2 价值主张拆解（可衡量）
1) **吞吐提升**：同一时间并行任务数提升（并行终端/任务 + 自动启动）。  
2) **打断降低**：审批次数减少、审批处理时间下降（规则/AI 决策 + 审批中心）。  
3) **风险降低**：高危操作被阻断/需要人工确认（可审计、可解释）。  
4) **复盘效率**：定位“为什么失败/卡住”时间下降（日志/审批/任务详情聚合）。  

### 5.3 建议的商业验证指标（MVP 级别即可）
- 每日并行任务峰值（P95）。
- 每任务的人工干预次数（审批/输入/修复）。
- 自动审批命中率（白名单/黑名单/AI 决策）。
- 失败原因分布（超时/权限/依赖缺失/环境问题）。
- 从“创建任务”到“完成/交付”的周期时间（lead time）。

### 5.4 潜在付费点（优先级从高到低）
- **团队功能**：多用户与权限隔离（已具备基础），共享看板/只读模式/审批协作。
- **治理与审计**：审批策略分级、审计导出、留存策略、SSO/LDAP（未来）。
- **远程执行**：SSH 目标管理、项目隔离、凭据管理、执行配额。
- **高可靠托管**：更强的恢复/重连/容错、任务 SLA、告警与通知（邮件/Slack/企业微信）。

## 6. 竞品分析（基于本地可访问证据）

### 6.1 Vibe Kanban（BloopAI）
证据：`/root/aicoding/vibe-kanban/README.md`
- 定位：多 agent 编排与“工程管理层”，强调并行/串行执行、快速 review、集中配置 MCP、远程 SSH 打开项目。
- 启示：  
  - “远程运行 + 本地 IDE 打开”是强需求；  
  - “集中配置”对团队规模化很关键；  
  - 更偏产品化与分发（npx 一键启动）。

### 6.2 CodeKanban
证据：`/root/aicoding/CodeKanban/README.md`
- 定位：统一页面管理 terminal 与 AI 工具状态（Claude/Codex），带历史、任务看板、worktree/notes。
- 启示：  
  - worktree/并行分支管理是常见高频诉求；  
  - “历史/对话追溯”是让用户持续使用的粘性点；  
  - “单文件部署”降低使用门槛。

### 6.3 Claude Code Workflow（CCW）
证据：`/root/aicoding/Claude-Code-Workflow/README.md`
- 定位：更“编排框架”而非轻量管理台，核心是 JSON 驱动、任务状态单一真相、搜索/记忆/多模型策略与 dashboard。
- 启示：  
  - 当用户规模化使用 agent 后，对“状态文件/工件/记忆系统”的需求会爆发；  
  - 但这类重体系对新用户门槛更高，通常需要强引导与更明确的价值证明。

### 6.4 竞品地图（建议的差异化策略）
ACA 可以占据的黄金位置：
- **比 CodeKanban 更强的治理/审批/审计与多用户**；
- **比 CCW 更轻量、更偏运维面与终端面**；
- **向 Vibe Kanban 学习分发与配置集中化**，但先把“终端/审批/托管稳定性”打磨到可信。

## 7. 可深化方向（按 ROI 与风险优先级排序）

### 7.1 P0：可靠性与闭环可控（决定能否商业化）
- 明确并降低 tmux 依赖：  
  - 若缺 tmux，UI/日志应明确提示“不可恢复”，并避免用户误解；  
  - 或提供替代持久化策略（如纯 PTY + 进程托管/屏幕录制式 replay）。
- SSH 会话恢复策略与边界显式化：  
  - 例如把 SSH 终端定位为“临时会话”，持久化依赖远端 tmux/screen；  
  - 或引导用户在远端自动创建 tmux session。
- 审批策略分级：  
  - 基于风险因素（写文件/执行 git push/rm -rf/权限提升等）强制人工确认；  
  - 给出“为什么需要确认”的可解释说明。
- 托管完成判定增强：  
  - 从单一标记（如 ACA_TASK_DONE）扩展为可配置组合：退出码、关键命令成功、测试通过、产物存在等。

### 7.2 P1：团队与运营
- 项目维度隔离：任务/终端/日志按项目归档；多项目切换。
- 审批中心协作：分配审批责任人、只读观察者、审批 SLA。
- 通知渠道：邮件/Slack/企业微信（闭环：需要干预/已完成/被阻断）。

### 7.3 P2：编排层与生态
- 工作流与任务体系收敛：给出明确用法（何时用 workflow、何时用 task）。
- 工件体系：自动归档关键 diff、命令历史、失败快照，形成“可复现”与“可交付”。
- worktree/分支并行管理（参考 CodeKanban/Vibe Kanban 的高频诉求）。

## 8. 当前闭环问题清单（需要产品化解决的点）

1) **会话恢复的环境依赖**：tmux 不存在时恢复能力不可用，需要显式提示与替代路径。  
2) **SSH 会话重启不可恢复**：需要更清晰的产品边界与引导策略。  
3) **多代理完整验证不足**：应优先收敛到 1-2 个最主流 agent 做深做稳。  
4) **工作流 vs 任务双体系**：若无明确分工，会造成用户认知负担。  

---

## 9. 可删除/降级（减少复杂度，提升主线完成度）

取决于短期定位：
- 若短期主打“终端托管 + 审批治理”，可将工作流/模板/AI workflow 入口收纳到“高级功能”或隐藏。
- 统计面板若不能驱动行动（告警/策略优化），可先保留最关键指标，避免维护成本上升。

## 10. 建议路线图（面向商业验证）

### 2 周：做一次最小商业验证
- 找 5-10 位重度 CLI agent 用户，记录：并行任务数、审批次数、被阻断次数、节省时间主观评分、失败原因。
- 目标：证明 ACA 能在 1-2 个明确场景带来可量化收益（吞吐提升/打断减少/风险降低）。

### 4-8 周：以“可靠性 + 治理”完成产品化
- 处理 tmux/SSH 边界、审批分级、托管判定增强、通知闭环。
- 输出可售卖的团队套餐（多用户/RBAC/审计导出/通知/远程执行增强）。
